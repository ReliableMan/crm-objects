# Решения и допущения

Там, где задание допускало разные трактовки, приняты следующие решения. Все правила доступа
реализованы в базе данных (`supabase/migrations/`); интерфейс только отображает то, что разрешено.

## Роли и пользователи

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Где хранится роль | В таблице `profiles`, а не в метаданных пользователя | Метаданные пользователь может изменить сам |
| 2 | Роль нового пользователя | Всегда «Исполнитель»; постановщика назначает администратор запросом в базе | Безопасное значение по умолчанию |
| 3 | Может ли человек иметь обе роли | Нет, роли взаимоисключающие | Проще и прозрачнее права |
| 4 | Кто видит список сотрудников | Все вошедшие видят имена и роли (email в профиле не хранится) | Нужно для истории и выбора исполнителя |
| 5 | Регистрация | Выключена; пользователей создаёт администратор | Требование задания |

## Задачи и объекты

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 6 | Исполнитель при создании задачи | Обязателен, только пользователь с ролью «Исполнитель» | Без исполнителя задача не может двигаться по статусам |
| 7 | Смена исполнителя | Только в статусах «Новая» и «На доработке» | Нельзя «отобрать» задачу в работе или на проверке |
| 8 | Что видит прежний исполнитель после переназначения | Перестаёт видеть задачу и её историю | Исполнитель видит только свои задачи |
| 9 | Редактирование задачи | Постановщик может править задачу в любом статусе, кроме «Принята» (в том числе на проверке) | Принятая работа зафиксирована; до приёмки описание можно уточнить |
| 10 | Удаление задачи | Только в статусе «Новая» | История выполненной работы не теряется; у новой задачи в истории только факт создания |
| 11 | Удаление объекта | Запрещено, если у объекта есть задачи | Не теряем задачи и историю |
| 12 | Что видит исполнитель на объекте | Только объекты, где у него есть задачи, и только свои задачи на них (в том числе в счётчике) | Требование задания |

## Статусы и история

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 13 | Как меняется статус | Только через функцию базы `change_task_status`; прямое изменение запрещено правами на колонку и триггером | Проверка перехода и запись истории в одной транзакции |
| 14 | Где описаны переходы | В таблице `status_transitions`; по ней проверяет база и рисует кнопки интерфейс | Одна точка правды |
| 15 | Кто принимает задачу | Любой постановщик, не только автор | Постановщиков может быть несколько, и каждый «видит всё» |
| 16 | Комментарий к переходу | Обязателен для «Вернуть на доработку», для остальных переходов не запрашивается | По заданию |
| 17 | Что пишется в историю | Только смены статуса (и создание задачи). Смена исполнителя и правки текста в историю не пишутся | В задании история — это история статусов |
| 18 | Одновременные действия | Строка задачи блокируется на время смены статуса | Двойной переход из одного статуса невозможен |
| 19 | Попытка действия с чужой задачей | Ответ «Задача не найдена», а не «Нет доступа» | Не раскрываем факт существования задачи |

## Инструменты администратора

- **Демо-данные** (`npm run seed`) создаются от имени настоящих пользователей через публичный ключ:
  объекты и задачи — от постановщика, смены статусов — от того, кому они разрешены. Сервисный ключ
  нужен только для создания пользователей и профилей. Так заполнение данных само проверяет, что
  права пропускают легальные действия. Повторный запуск ничего не дублирует; для пользователей,
  у которых нет профиля (например, после пересоздания базы), профиль создаётся заново.
- **Сброс демо-данных** (`npm run seed:reset`) — функция базы `admin_reset_demo`, доступная только
  сервисному ключу. Это инструмент администратора, а не возможность для пользователей: ни посторонний,
  ни исполнитель, ни постановщик вызвать её не могут (проверяется тестом). Пользователей и профили
  сброс не трогает; запрет на удаление начатых задач для обычных операций не ослаблен.
- Файл миграции сброса назван вручную (`20261116100300_…`): автоматическое имя по текущему времени
  оказалось бы раньше остальных миграций, и она применилась бы до создания таблиц.

## Технические решения по ходу работы

- **Тест безопасности** перед каждым сценарием ищет задачу в нужном статусе, а не полагается на
  исходные данные; если такой задачи нет, сценарий помечается как пропущенный, а не проваленный.
  Тест работает только с публичным ключом и не изменяет демо-данные (единственная создаваемая задача
  удаляется в конце сценария при любом исходе).
- Типы базы генерируются из схемы (`npm run gen:types`), а скрипты проверяются компилятором вместе
  с приложением в `npm run build`.
- После любого действия в интерфейсе обновляются все связанные списки (объекты, карточки, «Мои задачи»):
  статус задачи влияет на счётчики и видимость объектов.
- Права в интерфейсе — только подсказка: недоступные роли кнопки не показываются, но каждое действие
  повторно проверяет база.

## Что не сделано / можно улучшить

- Нет обновления в реальном времени: чтобы увидеть изменения другого пользователя, нужно обновить страницу
  (данные также обновляются при возврате на вкладку).
- Нет пагинации и поиска — для демо-объёма не нужны.
- Нет сброса пароля и управления пользователями из интерфейса — сотрудников создаёт администратор.
- Роль меняется только запросом администратора в базе.
- Нет e2e-тестов интерфейса — безопасность проверяется тестом на уровне API.
- Нет сроков, приоритетов и вложений в задачах (не требовались заданием).
- Изменения полей задачи (не статуса) не журналируются; при развитии — аудит всех изменений.
- Вместо удаления можно сделать архив.
